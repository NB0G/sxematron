# Трассировка на CPU и перспектива GPU

Компоновку ELK, трассировку и подготовку интерактивного SVG выполняют worker threads на сервере. После расстановки один проект может занять до восьми потоков: основной воркер трассирует часть листов, а до семи свободных воркеров — остальные. Общий лимит задаёт `SCHEMATIC_BUILD_WORKERS`. Если свободных воркеров нет, проект продолжает расчёт без ожидания помощников. На одном листе цепи прокладываются последовательно: от порядка зависят свободные коридоры, ответвления и места для меток. Браузер показывает готовый SVG и экспортирует файлы.

**Для сервера с 10 ядрами я бы пока оставил CPU.** Чтобы разрешить до восьми потоков на многостраничную схему, задайте в локальном `.env` параметры `CPU_LIMIT=8` и `SCHEMATIC_BUILD_WORKERS=8`. По умолчанию Docker ограничен двумя CPU и не переключается на восемь автоматически. Восемь — предел на один проект и общий бюджет при такой настройке: два клиента делят этот пул. Сравните время ожидания и расчёта (медиану и p95) и пик памяти при одном и двух клиентах; на маленьких схемах запуск воркеров и копирование данных могут стоить дороже самого расчёта.

Для ориентира: локальный синтетический прогон на Mac arm64 без лимитов Docker занял около 0,15 с для 100 компонентов и 200 автоцепей на 4 листах и 1,6 с для 500 компонентов и 1000 цепей в режиме меток на 20 листах. Это время ядра расчёта, без HTTP и очереди, не замер на целевом сервере. Для нескольких тяжёлых задач одновременно не забудьте про лимит памяти контейнера: на воркер ограничен старый JS-heap (192 МиБ), а фактическая память потока больше.

Диагностический заголовок `X-Schematic-Routing-Workers` показывает, сколько потоков выполнили части запроса построения. Если узким местом окажется один плотный лист, прежде GPU стоит попробовать пересчитывать лишь затронутые участки и цепи. Распараллеливание по листам такому проекту не поможет.

## Что улучшено

1. **Надёжность.** Закреплённый провод, проходящий через чужой компонент, отмечается предупреждением, но не меняется. Автотрассы получили короткие детерминированные ID, а добавление листов соблюдает лимит формата (200).
2. **Повторный расчёт.** Неизменившиеся листы могут переиспользовать результаты трассировки из RAM-кэша воркера (до 4 МиБ, до 30 секунд). Ключ включает геометрию, библиотечные определения, порядок листов и межлистовые связи. При промахе или смене воркера лист трассируется заново. Проверка входных данных, компоновка и подготовка SVG выполняются при каждом запросе.
3. **Плотные листы.** Компоновщик собирает небольшие кластеры по сигнальным связям, сравнивает горизонтальный, вертикальный и компактный варианты, а для последовательных резисторов пробует складывать цепочку в ряды. Выбор учитывает занимаемые габариты, расстояния между выводами и их направления; сдвиг группы дополнительно учитывает препятствия. Автоматический поворот не переопределяет явно заданный угол. При неудаче трассировки в небольшом проекте один повтор даёт проблемной цепи приоритет. Ручная проводка не перемещается; новая версия принимается только при улучшении диагностики. Это эвристики, не поиск глобально лучшей раскладки.

GPU имеет смысл испытывать, если профилирование покажет, что поиск на больших сетках регулярно исчерпывает CPU-бюджет. Тогда можно хранить компактную сетку занятости и стоимости на видеокарте и считать пакеты независимых поисков (например, волновое распространение по листам). Разрешение конфликтов между путями, детерминированную сборку и проверку связности оставить на CPU. Сравнивать нужно полное время, включая перенос данных и сборку результата: текущий A* ветвится, использует очереди с приоритетом и зависит от уже проложенных проводов, поэтому прямой перенос на GPU не гарантирует ускорения. CPU остаётся обязательным резервным режимом. GPU-реализации сейчас нет.

См. [Node.js: worker threads](https://nodejs.org/download/release/v24.22.2/docs/api/worker_threads.html) и [NVIDIA CUDA Best Practices Guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/).
