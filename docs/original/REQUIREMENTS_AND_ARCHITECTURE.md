# ГОСТ Схематика — согласованные требования и архитектура

**Статус:** ТЗ для новой разработки. **Приоритет:** прямые решения пользователя (особенно поздние) выше ранних предположений ассистента. **Язык интерфейса:** русский. **Платформа:** веб-приложение в Docker. **Главная цель:** получить редактируемую электрическую принципиальную схему по ЕСКД из машинного описания JSON, при необходимости вручную исправить размещение, скачать новый JSON и векторные SVG листов.

> Это описание — основание для реализации, а не утверждение о том, что все функции уже существуют. `reference/legacy_mvp` — только прежний экспериментальный прототип, НЕ итоговая архитектура и НЕ доказательство соответствия ГОСТ. При существенных конфликтах с ним реализовать данное ТЗ.

## 0. Непереговорные требования

1. Сайт — **редактор и генератор**, не схема из «нарисованных вручную линий без электрической модели». Электрическая связность хранится как компоненты, физические выводы и `nets` независимо от геометрии проводов.
2. Загрузить готовый JSON схемы, построить схему, автоматически расположить элементы, дать перемещать компоненты/секции и редактировать провода, экспортировать **SVG каждого листа** (ZIP при нескольких листах) и **текущий JSON**.
3. Веб-сайт **НЕ хранит проекты** и не предоставляет интерактивный текстовый JSON-редактор. Проект живёт в памяти открытой вкладки; импорт/экспорт JSON-файлом. При закрытии с несохранёнными изменениями — предупреждение. Сохранить проект в БД или список «Мои проекты» не делать.
4. **SQLite хранит только библиотеку компонентов** и необходимые служебные настройки/миграции, а не пользовательские схемы. Файлы БД и прочие персистентные файлы — в Docker volume. Один пользователь, без регистрации на первом этапе, дальнейшее расширение до нескольких пользователей не должно требовать переписывания электрической модели.
5. Каждый библиотечный физический компонент имеет **уникальный неизменный `component_code`**. Несколько предопределённых графических вариантов одного компонента имеют разные **`variant_code`** (подкоды). В JSON схемы ссылка **обязана** содержать оба кода. В каждом варианте одна или несколько секций с собственными постоянными `section_id`.
6. Многосекционный компонент — **одна физическая микросхема**, один набор физических выводов и одно позиционное обозначение при нескольких независимых графических секциях (например, 4 усилителя + питание). Размещение секций **на разных листах разрешено**. **Всегда выводить все секции** выбранного варианта, даже неиспользованные. Никакой генерации электрической обвязки неиспользованных секций: корректно подключить их должен автор JSON/инженер, не сайт.
7. В библиотеке только **жёстко заданные** УГО и варианты; генератор не придумывает новое представление, не меняет вариант автоматически и не произвольно делит корпус на секции. Новое УГО создаётся через конструктор вручную или импортом JSON компонента.
8. У выводов хранить номер/имя/геометрию/секцию. **Не вводить типы электрических выводов** `input/output/power/...` и не обещать ERC на их основе.
9. **Нет истории версий компонентов**. Используется текущее определение компонента. Изменения могут сломать старые схемы — тогда показать понятную ошибку ссылок/выводов, а не молча подменять соединения. Удалённые коды не переиспользовать.
10. **УГО по ГОСТ / ЕСКД**, чертёжный шрифт **GOST Type B**, рамки и основные надписи листов **А3, альбомная ориентация**, нумерация листов, межлистовые соединения, обычные проводники и именованные цепи. Степень соответствия конкретным ГОСТ проверяется позднее с пользователем по присланным эталонам; не заявлять без проверки стопроцентное соответствие.
11. **Нет UI для изменения ГОСТ-правил**: ни редактора нормативных линий, ни рамок, ни шрифтов. Пользователь позже даст точные визуальные эталоны, а ассистент **поправит исходный код** рендереров. Поэтому код рисования модульный и тестируемый; не путать с конструктором *самих* пользовательских УГО (он нужен).
12. Группировка по `tag` влияет на автоматическое соседство элементов, **видимые границы функциональных групп не рисовать вообще**. Поддерживать явно указанные координаты группы и/или компонента, и/или номер листа.
13. Смешанная компоновка: указанная пользователем жёсткая позиция/лист имеет приоритет; для остальных объектов — автоматическое размещение с учётом связности, направления прохождения сигнала, блоков, питания, длины проводов, препятствий, листов. Перемещённые вручную объекты при экспорте получают жёсткие координаты. Не менять ручную позицию молча.
14. Повторяемые шаблоны каскадов допустимы; раскрыть **все экземпляры** и **все физические элементы** на итоговом чертеже, создавая независимые локальные цепи и общие цепи только через явно назначенные интерфейсные порты.
15. Цепь может быть `wire` / `label` / `auto`, межлистовые соединения оформляются отдельно по ЕСКД, имеются специальные УГО и правила размещения для питания/земли. Геометрическое пересечение без электрической связи не превращается в узел.
16. Пользователь **пока не просит код дипломных компонентов**. Не импортировать/не создавать LMV7219, AD8429, ESP32 и компоненты его реального диплома в качестве готовой библиотеки; использовать для тестов вымышленные экземпляры. Старый прототип содержит пример с LMV7219 только как исторический артефакт, не обязательный набор для нового приложения.
17. Визуальный стиль **Google Material Design 3** (Material You), допускаются умеренные элементы Material 3 Expressive, адаптивный интерфейс, светлая/тёмная тема; на печатном SVG никаких интерфейсных цветов/рамок.

## 1. Пользовательский сценарий

**Создание библиотеки:** открыть «Конструктор компонентов» → нарисовать УГО примитивами или загрузить JSON определения → указать стабильный код (при создании сервер может назначить новый), модель, варианты графических представлений, все секции, физические контакты, точки подключения → проверить предпросмотр/ошибки → сохранить в SQLite. После успешного изменения каталог Markdown обновляется.

**Создание схемы:** скачать `SCHEMATIC_AI.md` и `COMPONENT_CATALOG.md`, дать их внешней нейросети вместе с пожеланиями → получить JSON → загрузить его через «Схемы» → валидация схемы и доступных кодов/подкодов/выводов → раскладка каскадов и секций по листам А3 → трассировка/метки → рендер → ручная правка на canvas SVG → скачивание исправленного JSON (жёсткие позиции + маршруты) и SVG/ZIP.

**Повторный импорт:** загрузить скачанный JSON → восстановить ручные позиции, физическую связность, номера листов, геометрию зафиксированных маршрутов. Автокомпоновка может передвинуть только незакреплённые элементы. При отсутствии нужного компонента/варианта — явно сообщить ошибку.

**Нельзя:** хранить схемы на сервере, считать группировочный `tag` электрическим соединением, скрывать неиспользованные секции, автоматически менять вариант УГО, терять соединения после drag, создавать электрические перемычки в геометрических пересечениях, объявлять недоказанное ГОСТ-соответствие.

## 2. Разделы интерфейса

1. **Схемы**: загрузка/скачивание JSON; список листов/выбор листа; SVG-полотно; масштабирование/панорамирование, сетка/привязка, выбор/drag/поворот компонента/секции, выбор/добавление/изменение цепей, ломаных и меток; `undo/redo`; пересборка незакреплённых; журнал ошибок; скачивание SVG листа или ZIP всех листов. Без текстового редактора JSON.
2. **Конструктор компонентов**: палитра линий, прямоугольников, окружностей, дуг, многоугольников, текста, выводов, групп; выбор, перемещение, поворот, зеркальность, выравнивание, привязка к сетке; управление физическими выводами и вариантами/секциями; импорт Component JSON и предпросмотр с валидацией; сохранение в библиотеку.
3. **Библиотека компонентов**: поиск по имени/коду/категории; все определения и варианты; предпросмотр секций/выводов; создать, копировать, редактировать, удалить с подтверждением; код неизменен.
4. **Документация ИИ**: просмотр, копирование и скачивание актуальных `SCHEMATIC_AI.md`, `COMPONENT_BUILDER_AI.md`, `COMPONENT_CATALOG.md`. Markdown-каталог генерируется динамически из SQLite. Показ шаблонов JSON и схем (`*.schema.json`) допустим как загрузка/просмотр документации, но не как интерактивный редактор.

### Material 3

Navigation rail/side drawer, toolbar и контекстные панели, theme tokens, светлая/тёмная тема, доступные контрасты, удобное управление мышью и клавиатурой. Чертёжное поле с белым листом, независимое от UI-темы. SVG экспорта чистый, без сетки, выделений, подсказок, цветных drag handles.

## 3. Стек и логическая архитектура

**Выбранный рекомендуемый стек:** монорепозиторий TypeScript; React + Vite + Material UI (или другой адаптируемый Material 3 toolkit при соблюдении M3); Node.js + Fastify API; SVG renderer shared package; SQLite (`better-sqlite3` либо иной устойчивый драйвер); Ajv/JSON Schema для валидации; ELK.js для начальной направленной компоновки + собственный grid/orthogonal router + placement constraints.

Рекомендуемые пакеты:

```
apps/web/                  React интерфейс, маршрутизация, редакторы
apps/server/               Fastify, SQLite, API, миграции, каталог Markdown
packages/schemas/          Schemas, shared types, JSON validation
packages/model/            Компоненты, секции, электрический граф, nets
packages/layout/           Каскады, страницы, anchors, constraints, ELK adapter
packages/routing/          Ортогональная трассировка, labels, crossing/junction
packages/render-svg/       Векторная геометрия, ГОСТ-чертёж, шрифт и экспорт
packages/gost-rules/       Кодовые нормативные константы, обозначения, лист А3
packages/catalog-docs/     Динамический COMPONENT_CATALOG.md
examples/                  Только синтетические тестовые примеры
scripts/                   Миграции, проверка/тесты
Dockerfile
compose.yaml
```

Это предлагаемый layout репозитория, не обязательное требование к буквальным именам файлов; функциональная изоляция обязательна. **Нет UI по настройке `packages/gost-rules`**: поздние эталоны от пользователя вносятся правкой кода и тестов.

### Деплой

Один docker container, фронтенд как статика сервером Fastify; volume mounted `/data`; SQLite `/data/library.sqlite`; приложение может слушать `0.0.0.0:3000` внутри контейнера, наружный порт конфигурируемый и лучше слушать `127.0.0.1` на хосте при внешнем reverse proxy. Секретов и пользовательских проектов в image нет. Для открытого Интернета — авторизация внешним proxy до будущего многопользовательского режима. Миграции БД идемпотентные, данные сохраняются при пересборке. Backup SQLite только корректным Backup API / VACUUM INTO при корректной синхронизации, не копированием работающего WAL-файла. Предусмотреть импорт/экспорт всей библиотеки.

## 4. Модель библиотечного компонента

### Ключевые сущности

- **ComponentDefinition**: `component_code` (стабильный уникальный код, не переиспользовать, например `IC00042` или `GEN_R`), название, категория, единые физические выводы (номер/имя), префикс позиционного обозначения, произвольная справочная информация без типов электрических выводов, набор вариантов.
- **DisplayVariant**: `variant_code` — уникален **внутри компонента**, содержит одно или несколько УГО-секций. Пример `01`: один общий прямоугольник; `02`: несколько усилителей + отдельное питание. Список вариантов **задаёт пользователь**, генератор сам не создаёт альтернативные варианты.
- **SymbolSection**: `section_id` внутри варианта (`A`, `B`, `POWER`), геометрические примитивы, локальные подписи и список выведенных физических контактов с локальной точкой подключения. Каждый физический вывод в пределах варианта должен быть представлен ровно один раз по умолчанию, если отдельно не разработана безопасная модель визуального дублирования одного электрического вывода.
- **ComponentInstance** в схеме: `id` (стабильный локальный ID), `component_code`, `variant_code`, номинал/модель при необходимости, группа, предпочтительные позиции/страницы секций, единое назначенное позиционное обозначение (например `DA1`). `id` не равен `DA1`: при перестройке нумерация может меняться, связь остаётся по `id`.
- **PlacedSection**: привязка к `instanceId + section_id`, координаты и ориентация на конкретном листе. Визуальные секции одного экземпляра могут располагаться на разных листах, но относятся к одному физическому объекту.

### Коды и совместимость

`component_code` обязателен при использовании в Schematic JSON. `variant_code` обязателен там же. Сервер может автоматически присвоить `component_code` при создании записи, но затем код не меняется. Удалённые коды резервируются как tombstone или коды выбираются гарантированно не переиспользуемым генератором. При изменении определения история не хранится: схема всегда получает текущее определение код+подкод, после валидации. Ошибки при несовпадении номера вывода/секции — блокировать генерацию с детальным отчётом. Рекомендуется предусмотреть необязательный fingerprint определения в JSON для диагностики изменений; **не** делать исторические ревизии или старые копии библиотеки.

### Универсальные и специальные компоненты

Набор стартовых *типовых* УГО: резистор, конденсатор (варианты по типу при необходимости), индуктивность, диод, транзистор, контакт/разъём, коммутация, источники, питание/земля, универсальный блок микросхемы с конфигурируемым набором выводов. **Универсальные R/C/L — одна библиотечная модель/шаблон на вид символа**, конкретные номиналы задаются в экземплярах. Специфические микросхемы задаются жёсткими определениями в библиотеке. Не создавать реальные дипломные микросхемы в начальной поставке.

### Конструктор: единицы и графика

Миллиметры, локальная геометрия компонента, чертёжная система координат, настраиваемая в коде сетка по умолчанию 2,5 мм с тонким шагом 1,25 мм (это удобство редактирования, не нормативный универсальный размер). Примитивы: сегмент/полилиния, прямоугольник, окружность, дуга, многоугольник, текст, группы/трансформации, поворот/отражение; точка подключения вывода — отдельная сущность. Нельзя загружать/выполнять JS/скрипты из JSON; набор примитивов whitelisted; текст экранировать, значения и количество элементов ограничить. Длина вывода, направление подключения, номер/подпись — визуальные свойства. Нормативные базовые размеры оформляются в коде. Конструктор позволяет делать несколько секций одного варианта и несколько вариантов физической модели.

## 5. Формат JSON проекта (контракт высокого уровня)

Финальную строгую JSON Schema сформировать в начале реализации. Примерный состав:

- `format_version` — версия **формата файла**, не версия библиотечного компонента;
- `document` — название, обозначение документа, основная надпись, разработчик/проверил/даты, листы А3 landscape, печатные единицы мм;
- `sheets` — страницы, `id`, ориентация, реквизиты; заданная страница обязательна только там, где пользователь её фиксирует;
- `groups` — `id`, `tag`/название, `sheet_id` при явной привязке, необязательные `position`, порядок и `locked`;
- `components` — `id`, `component_code`, `variant_code`, номинал/значение и текст, `tag`, `sections` c относительными/абсолютными координатами/листами/`locked`;
- `nets` — `id`, имя, режим `wire|label|auto`, множество электрических терминалов `(component_instance_id, physical_pin_number)`; пометки supply/ground и межлистовых продолжений;
- `templates`/`repeat_instances` — при необходимости описание повторяемых групп; после нормализации все экземпляры/элементы должны быть материализованы. Явно разделять локальные цепи экземпляра и общие порты;
- `layout` — настройки авторазмещения, приоритеты, жёсткие positions, пользовательские точки перегиба проводов/положение меток; только геометрия без изменения электрического графа.

### Координаты и фиксация

Все измерения в миллиметрах. Система координат листа — от верхнего левого угла листа; координаты группы/УГО могут быть относительными и пересчитываются явно по системе координат (не смешивать в одном поле). `position` без `locked` — предпочтительная подсказка; `locked: true` — строгое ограничение. **Любой элемент/сегмент, перемещённый пользователем вручную, при скачивании JSON получает фиксированную геометрию**. Если якоря/позиции конфликтуют с оформлением, выдать предупреждение вместо молчаливого переноса.

### Повторные каскады

Шаблон каскада определяет внутренние `components`, `nets`, порты. При создании `N` экземпляров генерировать уникальные стабильные instance IDs и локальные имена цепей (например `CH1_SIGNAL`, `CH2_SIGNAL`). Связи общих шин — **только через явно заданные порты/подключения**. В финальной схеме показывать все компоненты и все секции каждого экземпляра; никаких декоративных «×4» вместо электроэлементов.

### Документация для ИИ

- `SCHEMATIC_AI.md`: исчерпывающий контракт схем, правила страниц/групп/цепей/кодов и подкодов, физический вывод vs секция, примеры успешных/ошибочных схем, рекомендации по сигналам/питанию, все обязательные секции.
- `COMPONENT_BUILDER_AI.md`: контракт компонента с ID, вариантами/подкодами, секциями, формой, контактами, локальными координатами, границами, примитивами, правилами валидации и примером импорта.
- `COMPONENT_CATALOG.md`: **генерируется из актуальной SQLite** при чтении/скачивании, все коды+подкоды, модели, полные списки физических выводов и секций, к какой секции принадлежит каждый контакт, какие варианты доступны и как ссылаться из схемы. Не хранить редактируемый второй источник истины.

Нет необходимости в отдельном пользовательском `GOST_STYLE.md` или настройщике оформления. Допустима внутренняя dev-документация о модульном рендерере и связях с нормами.

## 6. Алгоритм размещения, трассировка, листы

Пайплайн: validate JSON → resolve library references and pin numbers → expand repeated stages → physical connectivity graph → assign unique positional designators → group by `tag` → respect section and group page anchors → estimate occupied rectangles (including texts) → pack on A3 sheets → directed layout (ELK) → resolve constraints (fixed placements) → orthogonal routing around obstacles → select long-net labels (`auto`) → inter-sheet continuations → render text, symbols, frame, main title → detect/report collisions/out-of-bounds/unrouted/ambiguous crossings → SVG.

Свойства:

- Сначала учитывать пользовательские листы; затем автоматически распределять незакреплённые группы по А3, избегая чрезмерных межлистовых соединений. Разделение группы возможно, если иначе она не помещается, кроме жёстко фиксированных элементов. **Не рисовать границы групп**.
- Сигнал — преимущественно слева направо; питание/земля — специальные УГО и правила; ни название цепи, ни внешний вид без явно указанной роли не должны менять электрический смысл.
- Электрическая цепь (net) может состоять из 2+ терминалов, одна net = одна электрическая общность. Отдельные графические маршруты/именованные метки лишь визуализация.
- `wire`: ортогональная линия/ветвление; `label`: имя цепи/стрелка или подходящее нормативное обозначение; `auto`: критерии длина, изгибы, пересечения, межлистовое соединение. Параметры и пороги алгоритма — в коде, без панели редактирования ГОСТ.
- Пересечения **разных** электрических nets не соединять. Узлы реального соединения отображать по правилам ЕСКД; на пересечениях избегать неоднозначности.
- Межлистовая net должна иметь указатели с адресом продолжения по применимым требованиям ГОСТ/ЕСКД, без обрыва connectivity graph. Автоматическая адресация по номеру листа и/или зоне листа после проверки с пользователем.
- После ручного перемещения: не удалять wires/nets; пересчитать незакреплённые маршруты, сохранить в exported JSON зафиксированные позиции и модифицированные маршруты. Два режима пересборки «сохранить правки» (по умолчанию) и «полностью перестроить» с подтверждением.

## 7. Оформление ЕСКД, SVG и смена правил в коде

Лист А3 420×297 мм, альбомная ориентация, графическая рамка и основная надпись с реквизитами, нумерация листов, надписи/позиционные обозначения и контакты. Шрифт GOST Type B, должна быть возможность векторизовать в контуры для переносимого SVG, и вариант SVG с редактируемым текстом. Лицензию на используемый файл шрифта проверить; не включать в дистрибутив запрещённые к распространению font files. Все размеры чертежа — миллиметры и viewBox, экспорт не включает интерфейсные элементы.

**Ключевое уточнение пользователя:** если позже он пришлёт точные примеры/требования ГОСТ, ассистент **редактирует исходный код** соответствующих модулей и тесты. Не создавать экран редактирования ГОСТ-оформления; не хранить «профили ГОСТ» как пользовательские редактируемые настройки. Нормативные параметры допускаются в кодовых константах/темплейтах для лёгкой исправляемости.

До реальной сверки не утверждать полное соответствие конкретному ГОСТ. Использовать применимые ГОСТы (например, 2.702/2.710/2.304 и серии УГО) в актуальных редакциях, сверять применимость и даты. Для экспериментальной геометрии предусмотреть визуальные golden-tests и числовые unit-tests. Оформление разнесённых составных частей и межлистовых связей требует отдельного тестирования по эталонам.

## 8. Проверки и сообщения об ошибках

Проверять: структура JSON и version; уникальность экземпляров/групп/net IDs; существование `component_code`, `variant_code`, `section_id`; корректность физических номеров пинов; покрытие всеми секциями выбранного варианта (все должны быть на схеме); недопустимые дубли физического вывода между секциями; несовместимые текущие определения БД; выходы за границы А3 и основную надпись; наложения компонентов и надписей; невозможно проложенные маршруты; разрывы межлистовых continuation labels; неразрешённые ссылки и координаты.

Отдельно: не пытаться проводить электрические типовые ERC-проверки `input-output-power`, поскольку электрические типы выводов принципиально не задаются. Неизвестный NC / пассивность можно документировать вручную без автоматических предположений.

## 9. План реализации с контрольными точками

**M0 Инфраструктура:** Dockerfile/Compose, volume SQLite, Vite/React/Material 3, Fastify, первый экран, интеграционные smoke-tests, миграции, README запуска. Не тянуть готовые компоненты диплома.

**M1 Библиотека и конструктор:** SQL + API; stable code/subcode; примитивы, секции, physical pins; import/validate Component JSON, редактор и предпросмотр, add/update/remove; генерация каталога Markdown и полные AI-инструкции. Входные контрольные синтетические компоненты и варианты.

**M2 Редактор схем MVP:** Schematic JSON + validation; все секции/позиционные обозначения, nets; ручное перемещение и базовое ортогональное соединение; скачать JSON + SVG. Без сохранения проекта на сервере/JSON text editor.

**M3 Авторазмещение и многолистовые схемы:** ELK adapter, constraints/locked, страницы, повторяемые каскады, power symbols, automatic wire/label/net routing, page references. ZIP export.

**M4 Соответствие и качество:** рамки и титульный блок А3, Type B, нормативные подробности после визуальных образцов пользователя, SVG font outlining, regression/golden tests, обработка сложных кейсов, документация.

Каждый этап должен иметь запускаемый демо-сценарий с искусственными компонентами. Не превращать неполный прототип в якобы завершённый ГОСТ-редактор. Сначала API/доменные модели и инварианты, затем UI и рендер; если собирать по вертикальным срезам, тестировать end-to-end.

## 10. Критерии готовности (acceptance)

- [ ] `docker compose up -d --build` запускает сервис; перезапуск сохраняет библиотеку в volume; схемы в БД не появляются.
- [ ] Добавить вымышленный компонент с кодом, `01` (общая секция) и `02` (A/B/POWER) через JSON и конструктор.
- [ ] `COMPONENT_CATALOG.md` немедленно отображает обе вариации, выводы и принадлежность секциям.
- [ ] Импорт схемы ссылкой на `component_code+variant_code` отображает **все** секции одной физической микросхемы, даже непроводимые; секции могут занимать разные листы, физическое обозначение единое.
- [ ] Вырезать/изменить вариант УГО и заново открыть старый JSON: при несовместимости сообщить ошибку; нет истории редакций.
- [ ] Импорт схемы R/C/L с разными номиналами ссылается на общие шаблоны.
- [ ] `tag` группирует близко, не создаёт нарисованного прямоугольника; координаты, `locked` и `sheet` соблюдены.
- [ ] После перетаскивания и маршрутизации downloaded JSON содержит фиксированные новые позиции, а при повторном импорте положение сохраняется.
- [ ] Повторить тестовый каскад трижды: разные локальные nets, общие порты работают, все физические компоненты нарисованы.
- [ ] `wire/label/auto` и межлистовые обозначения не меняют электрических связей.
- [ ] Экспорт одиночного листа выдаёт А3 SVG; нескольких — ZIP SVG каждого листа, корректные mm/векторные элементы, рамки, основные надписи и нумерация.
- [ ] На UI **нет** текстового JSON-редактора, сохранённых серверных проектов или панелей изменения правил ГОСТ.
- [ ] UI Material 3 и на русском, ошибки импорта и несовместимых пинов информативны.
- [ ] Тесты подтверждают электрическую связность при перемещении, разделённые секции, экспорт, проверки номеров и запрет несанкционированного подключения разных nets.

## 11. Чего сознательно НЕ делать

- Не создавать компоненты реального диплома пользователя до отдельного запроса.
- Не создавать GUI-настройку ГОСТ и произвольные правки стандарта конечным пользователем.
- Не хранить редакции/историю библиотеки, не хранить проекты на сервере.
- Не генерировать варианты УГО из даташита автоматически внутри сайта: JSON создаёт внешняя нейросеть, затем человек импортирует.
- Не скрывать «неиспользуемые» секции, не проектировать для них питание/обвязку.
- Не вводить `input/output/power` электротипы пинов.
- Не выводить рамки функциональных групп, не делать текстовый JSON-редактор.
- Не обещать полностью безошибочное авторазмещение любой произвольной схемы или ГОСТ-соответствие без проверки.
